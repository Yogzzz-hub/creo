## 1. Overview
This document defines the complete database schema for Creo. Every table, column, data type, constraint, relationship, index, and Row Level Security policy is specified here.
The AI coding agent must use this document as the authoritative reference for writing SQLAlchemy models, Alembic migrations, and Supabase RLS policies.

| Category | Details |
|---|---|
| Database | PostgreSQL 15 hosted on Supabase |
| ORM | SQLAlchemy 2.0 with async support (asyncpg driver) |
| Migrations | Alembic — all schema changes via versioned migration files |
| Connection | Supabase connection pooler (PgBouncer) in transaction mode for production |
| UUID generation | gen_random_uuid() — PostgreSQL native, no application-side UUID generation |
| Timestamps | All tables include created_at and updated_at. Stored in UTC. updated_at auto-updated via trigger. |
| Soft deletes | Accounts and clients use deleted_at (nullable timestamp) — never hard delete client data |
| Naming convention | snake_case for all tables and columns. Plural table names. |

## 3. Table Definitions

### 3.1 users
Core account table for all platform users — clients, team members, and admins. Supabase Auth manages authentication; this table stores profile and role data.

| Column | Type | Constraints | Description |
|---|---|---|---|
| id | UUID | PK, default gen_random_uuid() | Primary key |
| auth_id | UUID | UNIQUE, NOT NULL | Supabase Auth user ID — foreign key to auth.users |
| email | TEXT | UNIQUE, NOT NULL | User email address |
| phone | TEXT | UNIQUE, NULLABLE | Phone number — used for OTP auth |
| full_name | TEXT | NOT NULL | User's full name |
| business_name | TEXT | NULLABLE | Client's business name — required for clients |
| role | user_role | NOT NULL, default 'client' | User role — determines access level |
| account_status | account_status | NOT NULL, default 'pending_verification' | Current account lifecycle state |
| plan_name | plan_name | NULLABLE | Active subscription plan — null for non-clients |
| instagram_access_token | TEXT | NULLABLE, ENCRYPTED | Facebook OAuth token for Instagram publishing |
| instagram_user_id | TEXT | NULLABLE | Instagram Business account ID |
| razorpay_customer_id | TEXT | NULLABLE | Razorpay customer ID for recurring billing |
| stripe_customer_id | TEXT | NULLABLE | Stripe customer ID for international billing |
| two_fa_enabled | BOOLEAN | NOT NULL, default false | Whether client has enabled 2FA |
| deleted_at | TIMESTAMPTZ | NULLABLE | Soft delete timestamp — null means active |
| created_at | TIMESTAMPTZ | NOT NULL, default now() | Account creation timestamp |
| updated_at | TIMESTAMPTZ | NOT NULL, default now() | Last updated — auto-managed by trigger |

users.auth_id links to Supabase's internal auth.users table. All authentication is handled by Supabase Auth. The users table is for application-level profile and role data only.

## 4. Key Relationships

| Relationship | Type | Description |
|---|---|---|
| users → subscriptions | 1 : many | A user can have multiple subscriptions (historical) |
| users → questionnaires | 1 : 1 | Each client has exactly one questionnaire |
| users → team_members | 1 : 1 | Each team member has one extended profile |
| users → client_assignments | 1 : many (as client) | A client has multiple assignments (designer, video editor) |
| team_members → client_assignments | 1 : many | A team member can be assigned to multiple clients |
| users → content_plans | 1 : many | A client has one plan per month |
| content_plans → content_calendar | 1 : many | A plan generates multiple calendar entries |
| content_calendar → tasks | 1 : 1 | Each calendar entry links to one task |
| tasks → deliverables | 1 : many | A task can have multiple deliverables (revisions) |
| deliverables → deliverable_comments | 1 : many | Each deliverable can have multiple comments |
| deliverables → deliverables | self-reference | parent_deliverable_id links revisions to originals |
| users → tickets | 1 : many | A client can have multiple tickets |

## 6. Row Level Security (RLS) Policies
Row Level Security is enabled on all tables as a secondary guard. The primary security layer is FastAPI middleware (JWT role validation). RLS policies provide defence-in-depth — a bug in the API layer cannot expose other users' data.

All RLS policies use auth.uid() to match against users.auth_id. The Supabase service role key (used by FastAPI) bypasses RLS — this is expected and correct. Client-side Supabase calls (if any) are fully governed by RLS.

| Table | Operation | Policy |
|---|---|---|
| users | SELECT | Users can read their own row only. Admins can read all rows. |
| users | UPDATE | Users can update their own row only (except role and account_status — admin only). |
| questionnaires | SELECT | Clients read their own row. Assigned team members and admins read all. |
| questionnaires | UPDATE | Clients can update within 7 days of submitted_at. Admins can update anytime. |
| deliverables | SELECT | Clients read their own deliverables. Team members read deliverables they produced or are assigned to. Admins read all. |
| deliverables | UPDATE | Team members can update status on deliverables they produced. Clients can update status (approve/reject) on their own deliverables. Admins can update all. |
| tickets | SELECT | Clients read their own tickets. Assigned team members and admins read all. |
| ticket_messages | SELECT | Participants of the ticket (client + assigned team) can read. Admins read all. |
| ticket_messages | INSERT | Participants of the ticket can insert. Admins can insert on any ticket. |
| notifications | SELECT | Users read their own notifications only. |
| notifications | UPDATE | Users can update is_read on their own notifications only. |
| tasks | SELECT | Team members read tasks assigned to them. Admins and team leads read all. Clients have no direct task access. |
| announcements | SELECT | All authenticated internal users (non-client roles) can read. Clients have no access. |
| content_calendar | SELECT | Clients read their own calendar. Team members read calendar entries linked to their assigned clients. Admins read all. |
| escalations | SELECT | Admins and team leads read all. Other roles have no access. |
| leave_requests | SELECT | Team members read their own requests. Team leads read their department. Admins read all. |

## 7. File Storage Structure

| Bucket | Access | Max File Size | Contents |
|---|---|---|---|

## 8. Webhook Events
Payment webhooks are received by FastAPI and trigger database state changes. All webhook endpoints validate the provider signature before processing.

| Provider | Event | Action Taken |
|---|---|---|
| Razorpay | payment.captured | Update subscriptions.status → active. Update users.account_status → active. Trigger onboarding questionnaire step. |
| Razorpay | payment.failed | Update subscriptions.status → past_due. Send failure email + in-portal notification. |
| Razorpay | subscription.charged | Update current_period_start/end. Record payment in payment history. |
| Razorpay | subscription.cancelled | Update subscriptions.status → cancelled. Update users.account_status → lapsed. |

| Stripe | payment_intent.payment_failed | Same as Razorpay payment.failed for international clients. |
| Stripe | customer.subscription.deleted | Same as Razorpay subscription.cancelled for international clients. |
| Stripe | invoice.payment_succeeded | Update period dates and record payment. |
